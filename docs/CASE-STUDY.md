# Case study: a bilingual product site with no framework

## The problem

The brief was a site for a hardware brand: four machines that run open-weight language models locally, an operating system that ships with them, a case library, a company section, support and the legal set, in Portuguese and English, with a checkout at the end of the funnel. The visual reference was a product page from a company with a design team and a component library. The delivery constraint was one engineer, no design system, and no application server.

The obvious answer was a framework. I took the opposite, and this document is about what that bought and what it cost.

Two facts decided it. The first was that the site is mostly static: nothing on a product page depends on who is asking. The second was that the content changes in bursts and comes from the client in documents, spreadsheets and e-mails, which means the site's real problem is not interactivity, it is keeping forty-five pages per language consistent while the copy keeps moving.

## Constraints

No framework, no bundler, no runtime for the pages. Every page had to open from the file system before it was deployed, which rules out anything that requires a server to assemble markup. Assets arrived late: renders, photography and interface screenshots came after the pages were designed. Copy arrived in two languages at different times, so one language was always ahead of the other. The site had to be indexable from the first deploy, with canonical URLs and language alternates correct, because a hardware brand competes for search terms against content from companies with editorial teams.

And it had to be reviewable. One person, no QA, no staging environment with real traffic: the git diff is the review, and a change that touches forty pages must be legible as one decision.

## What was built

A generator pipeline in Python, and a static site that is its output.

Each page family has a script that takes a content dictionary and returns HTML. Sixteen of them: home, products, the compact line, specifications, the operating system section, the flagship, the model pages, about, the hubs, cases, growth pages, a latency demo, the legal set, a notebook composition and tag injection. Thirteen import the same shell module, which owns the header, the footer, the region bar and the purchase drawer. Content lives in dictionaries keyed by locale, next to the generator that consumes it. Cross-page facts live in dedicated modules: prices and product identity, model generation speeds, case entries and their relations, currency conversion.

`tools/build_all.py` runs the generators as subprocesses in a fixed order and stops on the first failure. After them, five post steps: interface images swapped for their English variants, social cards added where a page lacks them, a content hash appended to every CSS and JavaScript reference, the sitemap rebuilt from the files on disk, and the redirect map regenerated.

Around that: 19 stylesheets, 10 JavaScript files split by concern, and three serverless functions for the operations that need a secret, a signature or a catalogue the browser cannot be trusted with.

## The four hard parts

**Keeping numbers true in 90 places.** The same four figures appeared on the home page, on four model pages, in a comparison table, in the structured data and in the drawer. The first version had them typed into each page, and the comparison table ended up disagreeing with a model page. The fix was structural: one module owns the values, and every consumer imports it, including the JSON-LD builder and the specification panel. The interesting part is the discipline it forces: a number in prose also has to come from somewhere, so case narratives receive their figures as arguments. When the client changed a value, one edit propagated to both languages and every page type, and the diff proved it.

**Language pairing that survives missing pages.** Portuguese and English are not the same routes with a prefix. Two slugs are translated rather than transliterated, and some pages exist in one language before the other. The sitemap is generated by walking the published tree, skipping pages marked `noindex`, and pairing what remains by path identity, with an alias map for the translated slugs. Each page carries a canonical URL equal to its real path and three alternates, with `x-default` pointing at English. The failure mode I had to design against is a page that exists but should not be advertised, or a pair that looks complete and is not. Both are handled at build time, because at request time there is no logic to consult.

**Currency that computes.** Case pages talk about cost, savings and payback. Writing those figures by hand in two currencies produces two stories that disagree. Instead, values are stored once as integers in the operating currency, converted at build time with a fixed rate, rounded by band so the result reads as a round number, and formatted for the locale. Payback is derived: price in the page's currency divided by the monthly saving. The consequence is that the same case can show a different payback in each language, and that is correct, because each page closes its arithmetic in its own currency. Accepting a visible cross-language difference was the hardest editorial decision in the project.

**A hero that works before the renders exist.** The hero image is a transparent PNG that the parallax moves, and the ids the script targets sit on the `<img>` itself. When the file is missing, an inline error handler reveals a CSS-drawn chassis, and a mutation observer copies the transform from the image to the chassis so the motion continues. That gave a page that looked finished before the photography arrived, and it left a permanent constraint: the id cannot move to a wrapper, and the chassis must stay the image's previous sibling. It is documented as a rule that cannot be broken, which is the honest way to describe a decision that now costs maintenance.

## What changed on the way

The starting point was hand-edited HTML with a shared stylesheet, and an archived copy of those pages is still in the tree. The earliest generator was written for the four model pages, which were the most repetitive, and it carries the full page skeleton inline; the shared shell module came later, when the other families needed the same header and footer. The sitemap began as a hand-kept list and became a scan of the published tree once the list had gone stale more than once.

The language model was the other change. Translating copy string by string produces English that reads like translated Portuguese, so the two languages are written separately and kept side by side as dictionaries. A page is written twice by choice rather than once by formula, and the pairing between languages happens in routing and metadata, not in the copy.

The last change was scope: the site grew a case library, a business section and a legal set, and the generator count grew with it. That is where the pipeline paid for itself. Each new family was a script and a dictionary, not a new architecture.

## What I would do differently

I would put an HTML validator and a link checker in the pipeline. String concatenation means malformed markup is found by looking at the page, and at 90 URLs nobody looks at all of them. I would also add an incremental mode: a full rebuild rewrites every page, so diffs are large and a one-word change is indistinguishable from a restructure.

I would replace the content dictionaries with a real template language and a schema for the content model, because the dictionaries have no type and a missing key is a build-time exception. And I would generate a small set of page-level assertions from the same modules: that the price in the markup matches the price in the JSON-LD, that every internal link resolves, that every `hreflang` target exists. All of those are cheap at build time and expensive to find in production.

The framework question I would answer the same way. It would have replaced the generator layer with a dependency tree and would not have touched the problem that actually hurt, which was consistency of facts across languages and page types.
